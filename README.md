# Crosshair

An impact-attribution engine for Counter-Strike 2 demos.

Crosshair scrapes professional-tier Faceit matches, extracts every player
decision into a structured dataset, trains a win-probability (WP) model on
state snapshots, then scores each action by the WP delta it caused.

The result is a per-action "impact" score that answers questions like
*which player swung this round?* or *was that smoke actually useful?* on
millions of decisions automatically.

> **Data and trained model are not shipped with the repo** — they're
> generated by running the pipeline. Numbers below are from a reference
> run on 1024 matches; your scale is whatever you scrape.
>
> **Accuracy caveat (2026-08-01):** an audit found the win-probability model
> was training on two features that encode the round's outcome
> (`time_remaining_s` derived from the actual end tick, and a visibility
> lookup that reached forward in time). Both are fixed in the sampler, but
> any previously reported AUC — including the 0.896 below — was measured
> before the fix and is not a valid held-out number. Re-ingest and retrain
> to get a real one. See `docs/reviews/`.

---

## What you get after running the pipeline

- A SQLite database of high-ELO matches scraped from Faceit
- Structured **events** for every player decision (buy, engagement, utility, rotation, bomb)
  with `situation` / `action` / `outcome` JSON
- **Round-state snapshots** at ~1 Hz, doubling as WP training data
- A trained **LightGBM win-probability model**
- Per-event **impact scores** — `p_before`, `p_after`, signed delta

Reference run for context: 1024 matches → 2.8 M events / 1.2 M states. See the
accuracy caveat above before quoting any AUC figure.

## Architecture

```
Faceit API  ->  Playwright session  ->  .dem download     (--source playwright)
            \-> Downloads API      ->  .dem download     (--source api)
                                            |
                                            v
                          awpy parser  ->  pandas tables
                                            |
              +-----------------------------+-----------------------------+
              v                                                           v
   feature_extractor.py                                            state_sampler.py
   (player decisions)                                              (~1 Hz snapshots)
              |                                                           |
              v                                                           v
       events table  <------  score_impact.py  <------  win_probability.py
                                  (per-action                  (LightGBM,
                                   WP delta)                    GroupShuffleSplit
                                                                by match_id)
```

## Setup

```bash
python3.11 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt

echo "FACEIT_API_KEY=your_key_here" > .env   # from developers.faceit.com
```

Examples below use `.venv/bin/python` explicitly — bare `python` is not guaranteed
to be this interpreter, and mixing interpreters produces confusing numpy import errors.

**If you use the Playwright scraper** (`--source playwright`, the default), note:

- It drives **your real Chrome profile**
  (`~/Library/Application Support/Google/Chrome/Default`), not a throwaway one — so
  the automated browser shares every session you're logged into. Close Chrome before
  running, or it will fail to acquire the profile lock.
- It launches the installed **Google Chrome.app** at its default `/Applications`
  path, not a Playwright-managed browser, so `playwright install chromium` is not
  needed for this code path.
- You need a Faceit account logged into that profile.

`--source api` avoids the browser entirely and only needs `FACEIT_API_KEY` with
Downloads access granted.

## Getting started — from empty repo to scored events

```bash
# 1. Scrape a small batch first to verify everything works.
#    Opens Chrome — log in, press Enter, then leave it running.
.venv/bin/python src/main.py scrape --max-players 2 --matches-per-player 5

# 2. Check what landed.
.venv/bin/python src/main.py status

# 3. Train the WP model on the round_states you scraped.
.venv/bin/python src/main.py train --eval

# 4. Score every event with WP-before / WP-after / impact.
.venv/bin/python src/main.py score

# 5. Explore.
.venv/bin/python src/main.py top -n 10
.venv/bin/python src/main.py round <match_id> 5 --engagements-only
```

> **Known issue on a brand-new database:** `db._init_schema` does not yet declare
> the `p_before` / `p_after` / `impact` columns that `score` writes and that
> `status` / `top` read, so steps 4 and 5 fail on a freshly-created DB with
> `no such column: impact`. `.venv/bin/python test/test_invariants.py` reports
> this (and the converse drift on an older DB). A migration is pending.

Larger runs are the same command with bigger numbers — `--max-players 20
--matches-per-player 30` will yield a couple-hundred matches over a few
hours of scraping.

You can also drop a `.dem` file in manually instead of scraping:

```bash
.venv/bin/python src/main.py demo path/to/match.dem
```

## Full CLI

```bash
.venv/bin/python src/main.py status                         # DB stats
.venv/bin/python src/main.py scrape --max-players 10        # scrape Faceit
.venv/bin/python src/main.py scrape --source api            # ... via the Downloads API instead
.venv/bin/python src/main.py scrape --min-elo 2500 --region EU --start-offset 0
.venv/bin/python src/main.py demo path/to/match.dem         # process one local .dem
.venv/bin/python src/main.py train --eval                   # train WP model
.venv/bin/python src/main.py score                          # fill impact for all events

.venv/bin/python src/main.py top -n 10                      # biggest WP swings
.venv/bin/python src/main.py top --by negative -n 5         # worst player moments
.venv/bin/python src/main.py top --event-type bomb          # filter by event type
.venv/bin/python src/main.py round <match_id> <round>       # round play-by-play
.venv/bin/python src/main.py player <name>                  # aggregate by player
```

## Methodology notes

A few things that aren't obvious at a glance:

**Train/validation split.**  Round-state snapshots within a match are very
similar to each other — splitting them randomly leaks "the future of this
round" into training. Crosshair uses `GroupShuffleSplit(groups=match_id)`,
which puts whole matches on one side or the other. Naive row-level splitting
inflates AUC substantially; grouping by match removes that particular illusion
(but not the in-row leakage described below).

**Calibration over discrimination.**  Impact scoring needs *calibrated*
probabilities, not just good rankings. Ranking checks alone can't see this —
they all survive any monotone distortion of the output while every impact
delta silently changes — so the suite also bins real held-out states by
predicted probability and compares each bin against the observed CT win rate.
See [test/test_win_probability.py](test/test_win_probability.py).

**Leakage is not just about the split.**  `GroupShuffleSplit` stops a round's
own future leaking across folds, but it cannot help when a feature encodes the
outcome *within every row*. Two did, and were fixed: `time_remaining_s` was
computed from the round's actual end tick (short rounds are decisive rounds),
and the visibility lookup snapped to the nearest cached tick in either
direction, so pre-contact states were tagged with contact that hadn't happened
yet. Post-decision snapshots are also now excluded from training.

**Feature design.**  WP uses 33 features — 32 numeric plus `map` as a
categorical — spanning team state (alive, HP, armor, helmets, equipment value,
utility on hand), positional information (team centroid spread, distance to
bomb), and information asymmetry (enemies spotted, sounds heard within range).

## Project layout

```
src/
  main.py                  single CLI entry point
  scraper.py               Faceit API + Playwright demo discovery (--source playwright)
  faceit_api.py            Faceit Data + Downloads API demo source (--source api)
  pipeline.py              orchestrates scrape -> extract -> store; both sources meet here
  extract.py               awpy wrapper, .dem -> pandas tables
  feature_extractor.py     pulls decision events (buy / engagement / util / rotation / bomb)
  state_sampler.py         samples team state every ~1 s
  win_probability.py       LightGBM WP model (train / load / predict)
  score_impact.py          fills p_before / p_after / impact in events table
  db.py                    SQLite schema + insert helpers

test/                      plain scripts, not pytest — run each directly
  test_invariants.py       schema + feature-parity checks (stdlib only, no model needed)
  test_win_probability.py  WP output properties incl. a calibration check; needs a model
  test_local_demo.py       inspection script for a local .dem; --write-db to store
  test_scraper.py          manual check for demo URL discovery; opens real Chrome

docs/reviews/              dated codebase audits

data/                      (gitignored — generated by the pipeline)
  crosshair.db             SQLite store
  win_prob.lgb             trained model
```
